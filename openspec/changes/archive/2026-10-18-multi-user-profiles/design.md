## Context

См. `proposal.md` — Why. Текущее состояние, важное для решения:

- Единственный профиль: `note_learn/app.py` держит `DEFAULT_SAVE_PATH = Path.home() / ".note_learn_profile.json"` и вызывает `PlayerProfile.load(self.save_path)` / `self.profile.save(self.save_path)` в четырёх местах (`__init__`, `toggle_trumpet_mode`, `_finalize_answer`, `run`).
- `PlayerProfile` (`note_learn/curriculum.py`) — dataclass с полями `stars, xp, current_streak, best_streak, current_stage_idx, max_unlocked_stage_idx, with_trumpet, step_counter, note_progress` и методами `to_dict`/`load`/`save`. `load` уже устойчив к мусору: при любой ошибке возвращает `cls()`.
- `TrumpetLearningApp.__init__(save_path=..., assets_dir=..., audio_enabled=..., headless=...)`; тесты (`tests/test_app.py`) передают `save_path=tmp_path/"profile.json"` и ожидают, что файл появится.
- `AppScreen` — enum из 4 экранов; отрисовка идёт через `_draw_<screen>_screen`, клики — через `_click_targets` + `_trigger_action(action_id)`. Клавиатурный ввод текста в приложении пока не используется (только `event.unicode` для помп), поэтому ввод имени пользователя — новая подсистема.
- Основные спеки в `openspec/specs/` ещё не созданы (изменение `trumpet-learning-app` не заархивировано), поэтому `user-profiles` — новая capability.

## Goals / Non-Goals

**Goals:**
- Отдельный модуль хранения профилей с индексом и файлом на пользователя, устойчивый к повреждённым данным.
- Раздельный прогресс по пользователям без смешивания, с гарантией «минимум один пользователь».
- Экран управления пользователями (создание/переключение/удаление) с подтверждением удаления и вводом имени.
- Обратная совместимость: сигнатуры `PlayerProfile.load(path)`/`save(path)` и `TrumpetLearningApp(save_path=...)` продолжают работать, существующие тесты проходят без переписывания.

**Non-Goals:**
- Аутентификация, пароли, права доступа и сетевой/облачный обмен профилями.
- Одновременное ведение нескольких профилей в одном окне (активен ровно один).
- Синхронизация партитур, аудио-ассетов или настроек между профилями.
- Смена схемы прогресса (`note_progress`) — структура `NoteProgress` остаётся прежней.

## Decisions

### 1. Формат хранения: каталог `~/.note_learn/` с индексом и файлом на пользователя
- **Решение**: `~/.note_learn/users.json` — индекс (`{"version": 1, "active_user_id": "...", "users": [{"id", "name", "created_at", "updated_at"}]}`), `~/.note_learn/profiles/<user_id>.json` — прогресс в текущем формате `PlayerProfile.to_dict()`.
- **Почему**: отдельный файл на пользователя делает запись одного профиля независимой от других (повреждение одного файла не рушит остальных, см. требование устойчивости) и упрощает удаление. Индекс даёт порядок, имена и активного пользователя.
- **Альтернативы**: один общий `profiles.json` со словарём — проще, но одна ошибка записи/парсинга теряет всех; каталог выбран как более надёжный. Никакой БД — избыточно для нескольких локальных профилей.

### 2. Идентификаторы: slug от имени + счётчик, а не имя как ключ
- **Решение**: `user_id` — kebab-case от имени (`Маша` → `masha`/транслит, `nina`), при коллизии добавляется числовой суффикс (`nina-2`). Имя может повторяться, `id` — уникален.
- **Почему**: требование «совпадающие имена не смешивают прогресс» выполняется только при независимом ключе; при этом имена файлов остаются читаемыми и безопасными для файловой системы.
- **Альтернативы**: UUID — надёжно, но нечитаемо для родителя, который смотрит в каталог; берём человекочитаемый ключ с дедупликацией.

### 3. Активный профиль как состояние хранилища, а не `save_path`
- **Решение**: `ProfileStore` владеет активным пользователем; `TrumpetLearningApp` держит `self.store` и `self.profile` и при переключении перечитывает профиль из хранилища. `save_path` сохраняется как legacy-параметр для совместимости (см. решение 5).
- **Почему**: текущий `save_path` жёстко привязан к одному файлу; множественность требует единой точки, знающей и список, и активного пользователя. Заодно `profile.save(path)` заменяется на `store.save_active(profile)`.
- **Альтернативы**: держать `save_path` и подменять его при переключении — расползается по вызовам и не решает список/удаление.

### 4. Ввод имени и удаление — через новый экран `AppScreen.USERS`
- **Решение**: добавляется `AppScreen.USERS` + `_draw_users_screen`. Кнопка «Пользователи» в верхней панели (рядом с существующими «Карта курса» и «Все ноты и помпы»), кнопка «Новый пользователь» открывает inline-поле ввода (`event.unicode`, Backspace, Enter — подтверждение, Esc — отмена). Активный пользователь отображается в верхней панели. Удаление — кнопка у записи, требующая подтверждения вторым нажатием (в UI-состоянии, без модального диалога).
- **Почему**: соответствует существующему паттерну экранов и `_click_targets`, не тянет новых зависимостей; инлайн-подтверждение избегает модальных окон, которых в проекте нет.
- **Альтернативы**: текстовые поля pygame_gui — новая зависимость, не оправдана. Модальный диалог — ломает простую модель экранов.

### 5. Обратная совместимость и миграция
- **Решение**: `PlayerProfile.load(path)`/`save(path)` сохраняются как есть (используются хранилищем для чтения/записи файла пользователя). `TrumpetLearningApp(save_path=DEFAULT_SAVE_PATH)` сохраняет параметр: если передан явный `save_path`, не совпадающий с legacy-путём по умолчанию, приложение работает в режиме одного профиля по этому пути (как сейчас, чтобы не ломать тесты и внешний вызов). Каталог `~/.note_learn/` и миграция включаются, когда используется путь по умолчанию либо переданный `store`.
- **Почему**: `tests/test_app.py` и внешние вызовы передают собственный путь и ожидают файл профиля; «тихая» миграция на multi-user сломала бы их. Режим «путь по умолчанию → мультипрофиль» даёт новые возможности обычному запуску `uv run python main.py` без регрессий.
- **Миграция legacy-файла**: при инициализации хранилища по умолчанию, если `~/.note_learn/users.json` отсутствует, а `~/.note_learn_profile.json` существует — создаётся пользователь по умолчанию, в него переносится прогресс из legacy-файла (исходный файл не удаляется и не изменяется).
- **Альтернативы**: всегда мультипрофиль с принудительной миграцией — риск регрессии в тестах/автоматизации; отклонено.

### 6. Точки сохранения
- **Решение**: сохранять активный профиль в те же моменты, что сейчас (`_finalize_answer`, `toggle_trumpet_mode`, конец раунда, `run` finally) через `store.save_active(self.profile)`. Дополнительно при создании/переключении/удалении сохранять индекс и профили.
- **Почему**: минимизирует изменения в потоке приложения и сохраняет текущую частоту записи.

## Risks / Trade-offs

- [Регрессия в существующих тестах из-за смены механизма сохранения] → Режим совместимости по явному `save_path` (решение 5) сохраняет поведение `tests/test_app.py`; добавляются отдельные тесты хранилища.
- [Транслитерация русских имён в slug даёт странные имена файлов] → Ограниченный, предсказуемый маппинг (латиница + цифры), при невозможности — `user-<n>`; слаг вторичен, отображается всегда имя.
- [Повреждённый индекс `users.json`] → Чтение в `try/except`: при ошибке создаётся один профиль по умолчанию (требование устойчивости); повреждённый файл не удаляется автоматически.
- [Удаление активного профиля в момент записи] → Сначала переключаем активного на другого, затем удаляем файл; последний пользователь удалить нельзя.
- [Состояние ввода имени (кто в фокусе) усложняет обработку клавиш, которая сейчас сначала проверяет пробел/помпы] → Ввод имени обрабатывается первым и только когда активно поле ввода (`self.name_input_active`), иначе клавиши идут по прежней логике.
